# Bucket Counter (Android) — порт kun_front.py

Прототип Android-приложения, портирующего логику подсчёта ковшей с MaixCAM
(`kun_front.py`, AprilTag 36h11 + конечный автомат BELOW → ABOVE_CHECK → WAIT_RETURN)
на телефон: CameraX + ArUco-детектор из OpenCV for Android (модуль `objdetect`,
словарь `DICT_APRILTAG_36h11` — те же теги, что уже напечатаны, перепечатывать не нужно).

## Как собрать

1. Открыть папку проекта в Android Studio (Koala/Ladybug или новее) — она сама
   подтянет Gradle-обёртку и плагины по `settings.gradle.kts`.
2. Разрешить доступ к камере при первом запуске.
3. `minSdk 24`, `compileSdk/targetSdk 34`. OpenCV подключается как обычная
   Maven-зависимость (`org.opencv:opencv:4.10.0`), отдельный OpenCV Manager
   на устройстве не нужен — нативные библиотеки уже внутри AAR.

Этот код писался и проверялся без доступа к Android SDK/эмулятору в этой сессии,
поэтому это черновой, но цельный первый проход — см. раздел «Известные риски» ниже
перед тем, как считать его готовым к полю.

## Структура

- `BucketConfig.kt` — константы (ROI, положение линии по умолчанию, тайминги FSM) —
  перенесены из `kun_front.py` как доли от размера кадра, чтобы не зависеть от
  конкретного разрешения камеры телефона.
- `BucketCounterFsm.kt` — точный порт конечного автомата подсчёта.
- `FrameTransform.kt` — пересчёт координат между буфером анализа и экраном
  (предполагается `PreviewView.ScaleType.FIT_CENTER`, без обрезки кадра).
- `BucketAnalyzer.kt` — `ImageAnalysis.Analyzer`: YUV→grayscale Mat, поворот под
  экран, поиск тега в ROI через `ArucoDetector`, выбор лучшего по периметру
  (аналог `pick_target()`, но без `decision_margin` — см. ниже), прогон через FSM.
- `BucketOverlayView.kt` — отрисовка линии/ROI/рамки тега/счётчика/вспышки и кнопки
  LINE / RESET / −1 / +1, включая перетаскивание линии в режиме настройки.
- `MainActivity.kt` — разрешения, биндинг CameraX, сохранение позиции линии в
  `SharedPreferences` (аналог `/root/liney.cfg`).

## Калибровка под сценарий «кабина, через стекло, до 3 м»

Это главное отличие от MaixCAM-версии, где камера — отдельный промышленный модуль.
Телефон в кабине будет снимать ковш через лобовое/боковое стекло, и вот что стоит
проверить в первую очередь на реальном устройстве:

- **Автофокус.** Через стекло автофокус телефона может "гулять", цепляясь то за
  капли/грязь на стекле, то за отражения. Стоит зафиксировать фокус на дистанции
  ~2–3 м вручную (через `Camera2Interop` / `CaptureRequest.CONTROL_AF_MODE_OFF` +
  `LENS_FOCUS_DISTANCE`, либо `FocusMeteringAction` с однократным автофокусом и
  последующей блокировкой) — в текущем прототипе это не реализовано, камера
  работает в обычном непрерывном автофокусе CameraX.
- **Блики и отражения.** Не включать вспышку/фонарик (в коде она и не используется).
  Физически — поляризационная плёнка/чехол с присоской вплотную к стеклу снимает
  большинство бликов эффективнее любой программной обработки.
- **Разрешение анализа.** Поставлено 1280×720 вместо исходных 640×480 — на 3 м тег
  будет занимать заметно меньше кадра, чем на MaixCAM с более близкой установкой,
  и запас по пикселям тут важнее FPS (детект ArUco всё равно укладывается в реалтайм
  с большим запасом на любом современном телефоне).
- **ROI.** Пропорции ROI унаследованы от Python-скрипта (левая часть кадра, верхние
  80% высоты). Скорее всего их надо будет подвинуть под то, как ковш реально виден
  из кабины через выбранное крепление телефона — стоит включить режим LINE
  (кнопка в углу) и на месте посмотреть, где ковш пересекает кадр.
- **Экспозиция.** Если ковш попеременно оказывается на ярком небе и в тени кабины/
  кузова, автоэкспозиция может "прыгать" и терять тег на 1–2 кадра — если это
  станет проблемой, стоит зафиксировать AE так же, как и фокус.
- **Батарея/нагрев.** Постоянная работа камеры + CV будет греть телефон и сажать
  батарею — для стационарной установки в кабине разумно держать телефон на зарядке.

## Известные риски / что нужно проверить на устройстве

- **Имена классов OpenCV.** Используется API `org.opencv.objdetect.Objdetect` /
  `ArucoDetector` / `DetectorParameters`, появившееся после слияния модуля `aruco`
  в `objdetect` (OpenCV 4.7+). Если версия `org.opencv:opencv` в Maven Central на
  момент сборки окажется другой, возможны небольшие расхождения в именах —
  первое, что стоит проверить при ошибках компиляции.
- **Сопоставление координат.** `FrameTransform` предполагает `FIT_CENTER` без обрезки
  кадра — это должно давать точное соответствие, но поворот буфера анализа
  (`rotateForDisplay`) под конкретную ориентацию камеры/экрана стоит перепроверить
  на реальном устройстве (лёгкий сдвиг линии по вертикали — первый симптом
  рассинхронизации).
- **`decision_margin`.** В оригинальном скрипте `pick_target()` фильтрует теги по
  качеству (`dm < 0.18` — отбрасываем). Java API ArUco в OpenCV не отдаёт такую
  метрику напрямую; сейчас при нескольких найденных тегах с нужным ID выбирается
  тот, что крупнее (ближе/чётче), а слабые ложные срабатывания через стекло стоит
  давить через `DetectorParameters` (например, `minMarkerPerimeterRate`,
  `adaptiveThreshWinSizeMin/Max`), если они появятся на реальных кадрах.
- Код не собирался и не тестировался на устройстве в этой сессии (среда без
  Android SDK/эмулятора) — логика и API выверены по документации максимально
  внимательно, но первый прогон в Android Studio почти наверняка потребует
  мелкой правки-другой.
